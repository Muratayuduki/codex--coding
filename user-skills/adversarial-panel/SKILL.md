# Adversarial Panel

メインCodexをファシリテータとし、別プロセスのCodexを2〜3名のパネリストとして扱う。多数決を取らず、検証に耐えた根拠を残す。

## 不変条件

全ラウンドで次を守る。

- **独立性**: Round 1では、各パネリストに共通briefだけを渡す。他の回答、会話履歴、ファシリテータの見解を見せない。
- **敵対性**: 具体的な中心命題を攻撃させる。新しい根拠も検証もない同意を、批判ラウンドの成果として数えない。
- **平均禁止**: 投票、確信度の平均、折衷案で対立を消さない。根拠の強さを比較し、残る少数意見を明示する。

runnerはLinuxのbubblewrapを必須とし、パネリストごとにmount namespaceとPID namespaceを分ける。子Codexから見える分析資料は、read-onlyの `/workspace` と自分専用の `/panel` に限る。このほか、Codexとshellの実行、名前解決、TLS接続に必要な公開system pathだけをread-onlyでmountする。hostのHOME、共有record、他パネリストのartifact、別runのartifactはmountしない。認証ファイルはCodexの起動用にread-onlyでmountするが、filesystem permission profileでtoolからの読取をdenyし、`/proc` もdenyする。bubblewrapがない場合はrunnerをFail Fastで止め、隔離なしで子Codexを起動しない。

runnerで子Codexのuser config、apps、remote plugins、local plugins、plugin sharingを無効にする。子Codexにこのskillを起動させず、サブエージェントへの委譲や別パネルの再帰実行も禁止する。すべてのパネリストをファシリテータが直接起動する。

## Round 0: トリアージと構成選択

ユーザーが明示的にパネルを求めた場合は、自己評価の確信度にかかわらず実行する。

暗黙起動では、次の両方を満たすか判定する。

1. 誤答が費用、安全性、重要な設計、研究結論、重大な意思決定へ実害を与える。
2. 複数の合理的な見解が対立しているか、コード実行、計測、再計算、一次資料によって主張を検証できる。

両方を満たさない場合は直接回答する。ローカルコードまたは差分のレビューはこの判定から除外し、リスクに関係なく `review` skillを主workflowとする。本skillを併用するのは、ユーザーが明示した場合か、review findingsを独立検証する場合に限る。

課題の複雑さと損失に合わせ、構成を動的に決める。

| 区分 | パネリスト | 推論量 | 方法論 |
|---|---:|---|---|
| 標準 | 2 | `high` | `first-principles`, `outside-view` |
| 複雑 | 3 | `xhigh` | 上記2つと `falsifier` |
| 重大 | 3 | `max` | 上記2つと `falsifier` |

`ultra` は使わない。利用可能なモデルを実行前に確認し、可能な限り異なるモデル系列を割り当てる。同じ系列しか使えない場合は、モデル、推論量、方法論の順に差を広げる。ただし、この構成の収束を独立証拠として強く扱わない。

重大区分は、誤りが安全、法的義務、多額の費用、不可逆な操作へ直結する場合に限る。推論量やモデルが利用できない場合は黙って置き換えず、利用可能な構成へ縮退して実測構成を記録する。

## Brief

会話を見ていないパネリストだけで課題を解けるbriefを作る。次を含める。

- 正確な問い、必要な背景、対象パスや資料、制約、期待する出力
- 既知の事実と未検証の仮定を分ける指示
- 中心的な各主張に、確信度と具体的な反証条件を付ける指示
- 検証可能な主張を、コード実行、再計算、計測、一次資料で確かめる指示
- 他のパネリストを起動せず、このskillを再帰的に使わない指示

「反対の証拠が出たら」のような一般論を反証条件として認めない。失敗入力、反例、閾値、矛盾する一次資料など、観測可能な条件を要求する。

## Runner

skillディレクトリへ移動せず、briefを一時ファイルへ保存する。対象リポジトリや資料のルートを `--workspace` に渡し、runnerの絶対パスを使ってフォアグラウンド実行する。runnerにはLinuxとbubblewrapが必要である。角括弧内の第3パネリストは複雑または重大な課題で追加し、角括弧自体は入力しない。

```bash
python <skill-dir>/scripts/run_panel.py run --brief <file> --workspace <path> --panelist first-principles=<model-a>:<effort> --panelist outside-view=<model-b>:<effort> [--panelist falsifier=<model-c>:<effort>]
```

成功時のstdoutをJSONとして読み、`run_dir` と `record_path` を控える。`record_path` が指す `panel_record.json` から、`actual_configuration`、検証済みresponses、retries、failuresだけを統合用に読む。意図した構成ではなく、`actual_configuration` に記録されたモデル、推論量、方法論を実測構成として扱う。

統合に必要な情報を取り出した後、成功、縮退、中断のいずれでも一時記録を削除する。中断や予期せぬ例外でもstderrのrecord pathを回収し、その親ディレクトリを `run_dir` としてcleanupする。briefがrun directory外にある場合はbriefも削除する。

```bash
python <skill-dir>/scripts/run_panel.py cleanup --run-dir <run_dir>
```

## Round 1: Blind answers

runnerを使い、全パネリストをblindかつ並列で起動する。各パネリストには同じbriefと自分の方法論だけを渡す。

- `first-principles`: 前提を最小単位へ分解し、論理と観測事実から組み立て直す。
- `outside-view`: 類似事例、基準率、既知の失敗分布から見積もる。
- `falsifier`: 中心命題を反証する入力、証拠、実験を優先して探す。

### Validation gate

Round 1の各出力をRound 2へ渡す前に検証する。ステータス行、ツール通知、空の要約、エラーダンプを回答として扱わない。少なくとも結論、根拠、方法論に沿った検討、確信度、反証条件があることを確認する。

不合格のパネリストを同じ条件で一度だけ再実行する。それでも不合格の場合、3名構成で有効な2名が残れば縮退して続行し、脱落を統合で開示する。有効なパネリストが2名未満ならFail Fastで中止し、実行失敗として報告する。無効な出力を後続ラウンドへ混ぜない。

## Round 2: Cross-critique

各パネリストに、他の有効なRound 1回答だけを渡し、全peerを個別にassessmentさせる。次を命じる。

- 引用した具体的な主張に対し、事実誤認、弱い根拠、論理の飛躍、欠落した代替案、暗黙の仮定を指摘する。
- 検証可能な主張は、再実行、再計算、計測、一次資料の確認で攻撃する。
- 要約、称賛、同意の水増しを省く。攻撃と譲歩の双方に理由を付ける。
- 各peerの中心命題を攻撃する。有効な攻撃が成立しないpeerには `outcome=no-valid-attack` を設定し、試した反証方法と結果を記録する。

## Round 3: Final positions

各パネリストに、自分のRound 1回答へ向けられた批判を渡す。自分宛ての全critique IDに `concede` または `defend` で応答し、それぞれへ理由と根拠を付けさせる。最終見解、残余不確実性、確信度、具体的な反証条件に加え、`position_changed`、`position_change_source`、`position_change_reason` を明示させる。`position_change_source` は変更なしなら `none`、批判による変更なら `critique`、新しい証拠による変更なら `new-evidence` とする。`critique` の場合だけ根拠となったcritique IDへ `concede` し、`new-evidence` の場合は変更を正当化する具体的な新証拠を必須にする。

根拠の説明がない全面撤回を迎合の兆候として扱う。見解を変えた根拠を再提示させ、説明できない反転を統合の根拠から外す。

## 証拠重み付き統合

ファシリテータ自身の事前見解をパネリストの合意として混ぜない。追加見解が必要なら、ファシリテータの判断と明記する。

次の順で重みを付ける。

1. 再現可能な実行結果、計測、再計算、直接確認した一次資料
2. 検証済みの前提から導いた論証
3. 異なるモデル系列が独立に到達した一致
4. 同系列の一致、未検証の類推、直感

強い証拠と弱い推測を対等に並べない。証拠が一方を支持する場合は理由付きで裁定する。証拠不足で裁定できない場合だけ未解決とし、解決に必要な観測を示す。少数意見に検証可能な反例がある場合は残す。

## ユーザーへの回答

ユーザーの言語で簡潔に返す。逐語的な全討論は求められない限り載せず、次の順でまとめる。

1. 結論と確信度
2. 結論を支える最も強い証拠
3. 採用または棄却した主要な批判と理由
4. 未解決の対立、反証条件、次に必要な検証
5. 実際に走ったモデル、推論量、方法論と縮退内容

同意がなかった論点を全会一致と書かない。パネルの人数やモデル系列だけを権威として使わない。

## 縮退

runnerを使えない場合は、方法論ごとに厳密に分離した順次回答として実行し、同一モデルかつ共有文脈による弱い代替であると開示する。モデル系列を跨げない場合は方法論を変え、収束の証拠価値を下げる。有効なパネリストが2名未満なら討論を継続せず、Fail Fastで中止して実行失敗として報告する。

障害を隠すために空の回答を補完しない。失敗、再実行、縮退、脱落を `panel_record.json` と最終回答の実測構成へ反映する。
