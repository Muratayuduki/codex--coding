# Best Human UI

SHIGの100原則から、その作業に関係するものだけを選ぶ。原則の一覧を披露するためには使わない。利用者の目的、対象となるオブジェクト、操作、表示状態を具体的な判断へ結び付ける。

## 進め方

1. 対象の利用者、達成したいこと、利用環境、変更できる範囲を確認する。コード、画面、仕様など、実際に確認できた証拠を優先する。
2. [task-index.md](references/task-index.md) を読み、依頼に関係する公式タグを選ぶ。最初は1〜4タグに絞る。念のためという理由で全タグを選ばない。
3. 索引にある原則番号を、[model.md](references/model.md)、[interaction.md](references/interaction.md)、[presentation.md](references/presentation.md) から検索する。該当する項目だけを読む。
4. 原則が参照する理論や数値を詳しく確認する必要がある場合だけ、[related-sources.md](references/related-sources.md) を読む。
5. 選んだ原則を、設計上の決定または確認可能な指摘へ変換する。原則の要約だけで終わらせない。

## 設計と実装

- 情報モデル、操作順序、状態、フィードバック、文言について、実装前に制約を決める。
- 既存コードとデザインシステムがある場合は、その規則を先に確認する。SHIGを理由に一貫性を崩さない。
- 選んだ原則が判断を変えたときは、原則番号と決定内容を簡潔に示す。影響しない原則は出力しない。
- SHIGが扱わない視覚的な個性は `frontend-design`、shadcn固有の実装は `shadcn` に委ねる。

## レビュー

- 実際に確認できた問題だけを指摘する。画面を見ていないのに見たと仮定したり、実行していない挙動を断定したりしない。
- 指摘には、重要度、対象箇所、確認した事実、該当するSHIG番号と原題、利用者への影響、具体的な修正案を含める。
- 呼び出し元やリポジトリにレビュー形式の規約がある場合は、その重要度ラベルを優先する。規約がない場合だけ `[must]`、`[should]`、`[consider]` を使う。タスク失敗、データ消失、回復不能な操作、明示要件への違反は `[must]` とする。
- 問題がない原則や対象外の原則を列挙しない。全100件の監査表は、ユーザーが明示的に求めた場合だけ作る。
- 動的な挙動の確認が必要なら `ux-monkey-test` またはブラウザテストへ引き渡し、実測結果を静的な推測より優先する。

## 判断の優先順位

明示された要件、利用中のプラットフォーム規約、適用されるアクセシビリティ基準をSHIGより優先する。衝突した場合は、採用した規則と理由を示す。SHIGだけを根拠に、法令、WCAG、プラットフォーム規約への準拠を断定しない。
