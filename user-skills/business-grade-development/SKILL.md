# 実務向けの開発と検証

既存実装と既存テストが同じ誤解に基づいていても、業務上の欠陥を検出できるようにする。期待結果はコードの現状から逆算せず、確認した業務仕様と外部契約から定める。新規開発にも既存システムの強化にも適用する。

## 1. 業務と検証範囲を確認する

既存の仕様、関連実装、テスト、運用手順を必要な範囲で読み、分かっている情報は聞き直さない。不足する次の情報をユーザーに確認する。

- 何の業務で、誰が、何を完了するために使うか。利用者と管理者の権限、承認者、外部システムとの役割分担。
- 取り扱うデータ、業務状態と遷移、金額や数量の単位、締め時刻、取消・訂正・再処理のルール。
- 絶対に起きてはならない結果とその影響。例として、二重処理、残高不整合、他人のデータ操作、確定済みデータの消失。
- 想定件数、同時利用、応答時間、停止許容時間、復旧時点、監視担当と障害時の対応。
- 対象地域、契約上の条件、既存の社内規程、使用できる検証環境と外部接続の範囲。

仕様や安全性を左右する不明点は、依存する実装と合否判定の前に確認する。回答待ちでも、独立した調査や再現確認は進める。業務ルールや性能・復旧目標を推測で確定しない。

使用するテスト環境、許可された副作用、対象外の業務を明記する。このスキルの指定だけで、本番データ操作、実送金、デプロイ、破壊的な負荷・障害試験が許可されたと解釈しない。

## 2. 業務ごとの必須事項を調べる

対象業務が分かった時点で、公式の仕様、サービス提供者のAPI契約、行政機関や標準策定元の資料、提供された社内規程を調べる。最新性が必要な外部情報はWebで確認する。検索語には対象業務、対象地域、失敗条件を含める。

各確認事項に、出典URLまたはファイル行、確認日、適用条件を付け、次を分ける。

- 確認済みの業務要件または適用が確認できた必須事項。
- 技術上の推奨事項。
- 適用条件や業務判断が未確認の事項。

他業種のルールや一般的なチェックリストを、その業務の必須要件と断定しない。資料を取得できない場合は調査済みとせず、不足情報と判定できない項目を残す。法令等の適合性をテストだけで保証しない。

## 3. 実装前に詳細なテスト計画を作る

このスキルを使用する場合は、変更ファイル数にかかわらずテスト計画を残す。対象プロジェクト内の既存規約に合う場所へ置く。計画をGit管理外にする規約がある場合は、それに従って対象プロジェクトの `.gitignore` で明示する。

業務フロー、状態遷移、サービス間の境界、永続化の境界を整理し、守るべき不変条件を定義する。不変条件とは、処理中や障害後にも破ってはならない業務上の条件である。既存テストを対応付け、未検証の条件を見つける。

[境界と障害の観点](references/test-design.md)を読み、業務に関係する項目を具体的なケースへ落とす。主要なリスクを除外するときは理由を記載する。全項目の機械的な実行や、根拠のない全組合せ試験は求めない。

各ケースには次を記録する。

| 項目 | 内容 |
| --- | --- |
| IDと根拠 | 対応する業務要件、不変条件、出典 |
| リスクと優先度 | 失敗時の影響、発生条件、優先する理由 |
| 前提と入力 | 初期状態、権限、具体的な境界値、データ |
| 手順 | 操作順、同時実行の同期点、障害注入の位置 |
| 期待結果 | 応答だけでなく、永続データ、外部副作用、ログ、復旧後の状態 |
| 検証方法 | 単体・結合・E2E・運用試験の選択、環境、観測方法 |
| 結果 | 未実施・成功・失敗・実施不能、実行コマンド、証拠、修正との対応 |

同じロジックを期待値の算出に再利用しない。仕様から手計算した例、独立したモデル、不変条件の検査などを使う。重大な業務フローは、該当するDB制約、トランザクション、認可、外部契約を通る検証を含め、モックだけの成功を実環境との整合性の証拠にしない。

## 4. 検証し、修正して再テストする

まず既存テストを実行し、開始時点の失敗を記録する。重大な業務損失、認可違反、整合性破壊につながるケースから追加する。欠陥の修正前に、可能な限り失敗を再現する回帰テストを作る。自動化が難しい場合は、再現手順と合否を観測する方法を修正前に決める。

欠陥の原因を確認して依頼範囲内の最小修正を行い、失敗したケース、関連する境界ケース、影響する既存テストを再実行する。仕様変更や依頼範囲外の改修が必要な場合は、影響と選択肢を示して確認する。

テストを通すために業務上の期待値を実装へ合わせたり、検査を無効化したりしない。不安定な試験は成功するまで繰り返して済ませず、同期条件や原因を調べる。並行処理の試験には同期点を設け、可能な場合はseedや実行順を保存して再現可能にする。

テスト用データと隔離環境を使用する。実行できなかったケースは代替検証の範囲とともに記録し、成功扱いにしない。

## 5. 修正後のレビューを行う

利用可能なら `review` スキルを読み、修正箇所と、その修正が影響する業務フローをレビューする。利用できない場合も、以下の確認は省略しない。

- 元の欠陥の原因が解消されたか。同じ失敗が別の入口や再試行経路で発生しないか。
- テストの期待結果は業務仕様を表しているか。モックやfixtureが欠陥を隠していないか。
- 修正による認可、永続化、同時実行、性能、復旧手順への副作用はないか。
- 実装とテストが共有している前提を崩す反例がないか。

重大な業務リスクがある場合は、サブエージェントが利用可能なら `reviewer_deep` に独立レビューを依頼する。対象ファイル、業務要件、検証結果、変更禁止の範囲を渡す。利用できない場合は自己レビューであると明示する。

必須修正の指摘を解消し、関連テストを再実行したうえで変更後の差分を再レビューする。未解消の重大欠陥や必須の未検証事項がある場合は、完了または本番利用可能と判定しない。

## 6. 結果を報告する

発見した欠陥と業務への影響、修正内容、実行した試験と結果、レビュー結果、残る未検証事項を報告する。計画と証拠の保存先を示し、机上確認、モック試験、実際の結合試験を区別する。テスト件数やカバレッジ率だけで実務品質を保証しない。
