# 境界と障害の観点

業務仕様に適用できる観点を選び、入力値だけでなく状態、時刻、権限、同時実行、障害位置の境界を検証する。各観点の期待結果は対象業務の仕様で確定する。

| 観点 | ケースの組み立て方 |
| --- | --- |
| 値と表現 | 下限・上限の直前、ちょうど、直後。ゼロ、負数、空、欠損、小数精度、丸め、桁あふれ、単位や通貨の不一致。金額には業務上の最小単位を使用する。 |
| 状態遷移 | 許可・禁止される遷移、未承認、処理中、完了、取消、失敗、成否不明。終端状態への再操作と古いバージョンからの更新。 |
| 権限と分離 | 未認証、権限違い、他利用者・他組織のID指定、管理経路の直接呼出し、確認後の権限変更。UIで隠すだけでは防げない操作も試す。 |
| 重複と再試行 | 二重クリック、同一要求の再送、別内容で同じ冪等キー、同じキーを別利用者が使用、再起動後の再送、保持期間の境界。応答と業務上の効果の双方を確認する。 |
| 並行操作 | 同一残高・在庫・予約枠に対する競合、更新の取りこぼし、確認と更新の間の変更、デッドロックと再試行。別接続や別ワーカーを使用して本来の競合境界を通す。 |
| 途中障害 | 検証後、書込み間、commit前後、外部処理の前後、応答前で失敗させる。ロールバック、補償、成否照会、再処理で整合性が保たれるかを確認する。 |
| 外部連携 | タイムアウト、成功後の応答喪失、重複・逆順・遅延イベント、署名不正、部分応答、レート制限。タイムアウトを処理失敗と同一視しない。 |
| 時刻 | 有効期限や締め時刻の前・ちょうど・後、日付変更、タイムゾーン、休日、時計ずれ。対象地域で関係する場合は夏時間も扱う。 |
| 運用と復旧 | 監視と通知、追跡可能な監査証跡、ログへの機密情報混入、バックアップの復元、再起動、滞留処理、再処理権限、照合と手動復旧。復元できたという証拠と復旧後の整合性を確認する。 |
| 容量と性能 | 合意した件数・同時数での応答、キュー滞留、接続枯渇、タイムアウト後の状態、過負荷からの回復。許可された隔離環境と負荷上限を設定する。 |

## 送金業務での具体化の例

以下は検証の着眼点であり、すべての送金サービスに共通する仕様ではない。手数料、信用枠、保留、外部決済の仕組みなどを確認して期待値を確定する。

- 残高100、信用供与なし、手数料なしという仕様なら、80の送金を2件同時に要求しても両方が成立しないことを検証する。HTTP応答に加えて、残高、取引状態、台帳、外部指示数を確認する。
- 同じ送金要求を、初回の処理中と完了後に再送する。受付番号の一致だけでなく、引落しと外部送金が重複しないことを確認する。
- 外部では送金が成立したが応答を失った状況を再現する。照会や照合で成否を確定するまでの状態、再送可否、二重送金を防ぐ仕組みを確認する。
- 同一DB内の引落しと入金が原子的である仕様なら、その間の障害で片側だけが確定しないことを確認する。外部連携をまたぐ場合は、保留・補償・照合の契約を確認して検証する。
- 最小送金額、限度額、手数料を含む必要残高の直前・一致・直後を試す。丸め規則と台帳を含め、仕様に対応する資金の保存条件を独立に検査する。
- 他人の口座ID、同一口座間、停止中口座、承認前の要求、確定後の取消について、定められた業務ルールを検証する。

ほかの業務では、予約枠や在庫の二重消費、申請の自己承認、請求の二重発行など、その業務で失ってはならない条件に置き換える。
